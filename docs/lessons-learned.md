# 经验与踩坑

这个项目在 2026-09 的开发过程中犯过一批错。**记下来不是为了自嘲，是因为其中大多数
不报错、不崩溃，只是悄悄地把结果变差** —— 这类错误重复一次的成本远高于写下这段文字。

按类别分：**流程**（做错了方向）、**构建与工具**、**前端**、**AI 算法**、**测量与验证**。

---

## 一、流程：最大的浪费来自"没先说清理解"

### 1. 同一个需求理解错两版，白写两轮代码

**现象**：需求是"困难档的新方块生成位置要更难"。我先后按"贴着最大块"和
"两侧数字不同"实现了两版，**两版都理解错了**，白写两轮代码、两轮对拍、两次改前端镜像。

**根因**：拿到模糊需求（"大概""应该是""要那种感觉"）就动手，没有先把理解讲出来。

**教训**：规则/策略/手感类改动，先复述理解 → 等用户判断 → 再动手。
已写成硬规则（见 `AGENTS.md` 的"改代码前先讲理解"）。

### 2. 三个下拉框的备注：改了四轮才改对，因为**改错了文件**

**现象**：用户要求"三个下拉框里的备注文字统统删掉"。我反复修改 `config.js` 的数据层
（去掉 label 里拼的备注、把说明挪进规则弹窗），但界面**一点没变**。用户提了四次。

**根因**：备注**根本不是 `config.js` 拼的**，而是 `main.js` 的 `fillSelect`：

```js
node.textContent = option.note ? `${option.label}（${option.note}）` : option.label;
```

三个下拉框共用这一个函数。我改的那一层不参与显示。

**教训**：**"改完没生效"要先去读渲染路径，不要在数据层反复猜。**
这条现在有测试锁住：源码方向（`fillSelect` 里不许出现模板串）+ 数据方向
（真 `import config.js`，断言 label 不带括号）。

### 3. "下拉框"与"下拉框选项"是两个东西

**现象**：用户说"下拉框颜色突兀"。我改了容器（`<select>` 那个胶囊）的样式，
用户说"下拉框你不要调，调回去"。

**根因**：用户指的是**展开后的选项列表**（浏览器默认白底），不是容器。
原生 `<option>` 由操作系统绘制 —— 只能上色，不可能做成真透明。

**教训**：UI 反馈里"某个控件的颜色"可能是它的一部分而不是整体。
**歧义时必须列两种解释让用户选**，不要自己挑一个。

### 4. 连续四轮"图标的颜色未变动"

**现象**：用户三次说图标颜色没改。我每次都在 `rgba(255,252,247,0.x)` 里动小数点。

**根因**：两层。
① **色相根本没变** —— 小数点后的透明度变化肉眼看不出来；
② 更隐蔽的是 `#ai-auto`（AI操作）的图标**从页面打开的第一帧起就不存在**：
`newGame()` → `stopAuto()` → `el.aiAuto.textContent = '▶'`，
而按钮的 `textContent` 是**整个按钮的文本**，一赋值就把里面的 `<svg>` 全删了。
**颜色代码是对的，但那个图标早就不在 DOM 里。**

**教训**：① 调"颜色"要动色相，不要动透明度；
② 判定"元素在不在"必须量 DOM，不能读源码觉得对。
现在有断言：带内联 SVG 的按钮不许被写 `textContent` / `innerHTML`。

### 5. 我把自己套进了"内容超过一屏"的错误前提

**现象**：为让手机端棋盘上下居中，我推导出"内容总高超过一屏，必须缩小棋盘"，
并把这个结论当成约束去和用户讨论取舍。用户回："怎么会超过一屏，这不可能。"

**根因**：我给两个盒子各分了 `flex: 1`，**自己把空间吃掉了**，于是看起来没地方可分。
内容其实只有约 700px，一屏 915px。

**教训**：当推导出的结论是"做不到"时，先怀疑自己的模型 ——
尤其是我**自己刚加进去的**那些中间层。

### 6. "打断动画"降延迟：修一个问题，造一个更严重的

**现象**：为降低操作延迟，把"动画期间丢弃输入"改成"打断上一次动画再走这一步"。
结果渲染层被弄脏：**同一格出现两个方块**。

**根因**：走子时会把每个方块的 `row/col` **就地改成目标格**（这样轨迹索引才对得上），
然后才等 CSS 过渡。此时若被打断，下一次走子取"走子前棋盘"快照拿到的是
**已经改过的坐标**，收尾逻辑于是又往那些格子补了一块。

**教训**：**已经做对的机制不要为了"优化"轻易推翻**（输入锁是早期踩坑后做对的）。
真要改，先想清楚"被中断时中间状态是否自洽"。
已回退，并把"这条路为什么走不通"写进 `renderer.js` 的注释。

## 二、构建与工具

### 7. PowerShell 5.1 按 ANSI 读 `.ps1`，中文直接让脚本语法错误

**现象**：写的 `.ps1` 里有中文注释/字符串，运行报
`The string is missing the terminator` 之类的语法错误。

**根因**：Windows PowerShell 5.1 默认按 ANSI 读取无 BOM 的 `.ps1`，
UTF-8 的中文变成乱码，引号配对被打乱。

**教训**：**仓库里的 `.ps1` 一律纯 ASCII**（现有三个脚本都是这么做的）。
需要中文就写在 `.md` 里。

### 8. 用 PowerShell 重定向写文件，把 `style.css` 写坏了

**现象**：`Get-Content -Raw | Set-Content` 改几处时长，结果**中文注释全变乱码**、
文件被加上 BOM。

**根因**：PS 5.1 的 `Get-Content` 按 ANSI 读 UTF-8 → 内存里已经是乱码 →
`Set-Content -Encoding UTF8` 再写成带 BOM 的 UTF-8。

**教训**：**改文件用编辑器工具，不要用 PowerShell 重定向**（全局 `AGENTS.md` §12 已写）。
已 `git checkout` 恢复，改用编辑器逐条改，并复查"无 BOM / 中文完好 / 括号平衡"。

### 9. `.gitignore` 的 negation 陷阱：父目录被排除，子路径就再也放行不了

**现象**：要让 debug APK 进仓库，写了 `!android/app/build/outputs/apk/debug/`，
无效。`git check-ignore -v` 指向的是**顶层那条 `build*/`**。

**根因**：`build*/` 为了盖住 `engine/build` 与 `engine/build-tests` 而写，
`*` 把 `android/app/build/` 一起吃了。而 gitignore 的规则是
**父目录一旦被排除，git 根本不会往里看**，negation 形同不存在。

**教训**：① 排查用 `git check-ignore -v <路径>`，它会指出**真正生效**的那条规则在哪个文件哪一行；
② 构建目录**逐个列出**，不要用通配符图省事。

### 10. Android 构建环境的三个坑

| 坑 | 现象 | 修法 |
|---|---|---|
| 没钉 `ndkVersion` | AGP 用默认版本 27 并触发约 1GB 下载，而本机已装 29 | 显式写 `ndkVersion '29.0.14206865'` |
| CMake 只能从 SDK 找 | 联网下载**卡住不动**（`.temp` 几分钟 0.5MB） | `local.properties` 的 `cmake.dir` 指向本机 CMake |
| `-DAI2048_ENGINE_DIR` 手数 `../` | **数错两次**（得到 `E:\DeepSeekProjects\engine`、`E:\engine`） | 用 `rootProject.projectDir` 推导，不手数 |

**教训**：报错"目录不存在"**不会告诉你差几层**。能用框架给的绝对路径就别自己拼。

### 11. Gradle 构建产物路径不能硬编码

`.cxx` 中间目录名是**哈希**（`1c6d393x` → `pc133f46`），换次构建就变。
写脚本/文档时要用 glob 或相对路径，别抄那个哈希。

### 12. 两个 NDK 版本同时存在，用哪个要显式说明

本机有 `27.0.12077973` 与 `29.0.14206865`。不指明时 AGP 按自己的默认走，
于是"明明装了 NDK 还要下载"。**版本要用哪个是配置问题，不是环境问题。**

## 三、前端

### 13. 写死了 `el.xxx` 却指向不存在的 id

**现象**：`el.seedShown`、`el.difficultyNote` 指向 HTML 里根本没有的 id，
靠 `if (el.x)` 兜着所以不报错，只是那段逻辑永远不执行。

**教训**：死引用会**掩盖真实的拼写错误**。现在的测试检查"每个 id 都真实存在"。

### 14. `difficultyOptions()` 被声明了两次

**现象**：`SyntaxError: Identifier 'difficultyOptions' has already been declared`，
整个模块加载失败。

**教训**：前端没有编译步骤，类错误只能靠**加载即测试**发现（`node --check` + 测试套件）。

### 15. 分数框"矮一点"改了四轮，因为怀疑对象错了

**现象**：用户要求分数框矮一点。我反复改内边距和字号，框高**钉在 59px 不动**，
于是判断"高度不是内容撑的，是 flex 拉伸"，还改了 `.scores` 的 `align-items`。

**根因**：那个判断**是错的**。把滚轮区临时改成 `position:absolute` 后框高立刻变成 28，
证明它确实是内容撑的（8+12+31+8=59）。**是我的测量方法有问题**。

**教训**：**测量脚本本身也要被验证**。改一个值、量一次、发现没变时，
先确认"我改的是不是生效的那一处"，而不是直接跳到结构性结论。

### 16. 分数框内部居中的真正约束：11px 中文的文本高就是 14px

行高压到 12px 时文字会**溢出 2px 被裁**。所以"再矮只能减内边距"，
内边距最后只剩 4px。想要更矮就只能减字号 —— 那是"看不看得清"，不是空白。

### 17. 标题 `clamp()` 的系数凭感觉写，等于没生效

**现象**：为了让标题在窄屏收缩，写了 `clamp(30px, calc((100vw - 230px) * 0.62), 64px)`。
结果**任何屏宽都顶到 64px**。

**根因**：360px 时算出 80.6，早超上限。系数必须**由两个目标点解出来**：
（360 → 41px、560 → 64px）⇒ 斜率 0.115、截距 -0.4。

**教训**：`clamp` 的系数不要凭感觉；写之前先在纸上算两个端点。

### 18. 把"2 前面的空白"算成 48px，把标题推歪了 45px

**现象**：用户要标题的"2"对齐棋盘左边界。我用"元素宽度 − 文字宽度"
（202 − 154 = 48）当字形留白，加负 margin，结果标题被推左 45px，用户一眼看出。

**根因**：那 48px 里混进了**右边留白和字距**，不是左侧字形留白。
真实的左侧留白只有 **3px**（字形墨迹左边界 − 文本盒左边界）。

**教训**：这类几何量要**直接量**（`Range.getBoundingClientRect()` / canvas `measureText`），
不要用两个别的量相减去推。

### 19. 拖到一半的过渡被 CSS 打断：方块停在半路

**现象**：压测快速连滑（20ms/40ms 一次）时出现"重复位置"。

**根因**：被中断的滑动，CSS 过渡停在半路，方块视觉上挤在两格之间。

**教训**：**打断动画必须"落位"** —— 不加过渡地写一次 `transform`，把账当场结清。

### 20. 用 `window.innerHeight` 判"是否居中"，越调越歪

**现象**：手机端棋盘居中，我按 `innerHeight` 算偏差，在 Pro Max 上显示"偏 121px"，
于是继续调 —— 越调越歪。

**根因**：Playwright 的移动仿真里 `innerHeight`（1123）**明显大于**设备可视高
（`100dvh` = 932）。**判据和公式用的不是同一个量**。

**教训**：量布局要用 `100dvh` / `clientHeight`，别用 `innerHeight`。

### 21. 自己的旧进程在发旧文件，量了半天全是假数据

**现象**：改完 HTML 后反复量，数字**一模一样到小数点**。以为改动没生效。

**根因**：3011 端口上跑的是**更早启动的服务器进程**；新起的服务器因端口被占用
静默退出，一直在发改动前的 HTML。

**教训**：**测量前先确认被测对象是当前版本**。现在校验脚本第一行就断言
"服务器发来的 HTML 含某个本次新增的标记"，否则直接退出。

### 22. `Select-String` 过滤没匹配到就返回非零，被我当成测试失败

一次 `node tests/config.test.mjs | Select-String '✗'` 没有输出 + exit 1，
我误以为测试挂了。实际是 **`Select-String` 自己找不到匹配**时的退出码。

**教训**：看退出码要分清是**哪条命令**的。

## 四、AI 算法：三个"不报错、只变弱"的坑

### 23. chance 节点的 P(4) 写死 0.9/0.1

位置权重早就按难度接上了，**数值概率漏了**。实际是 10/15/20%。
后果不是"略弱"，而是**系统性偏乐观** —— 4 比 2 难缠，低估 4 等于告诉 AI"冒险划算"。

**教训**：AI 的"世界模型"必须等于实际游戏规则，否则概率不对、一切都错。
现在由 `FourSpawnProbability(difficulty)` 统一提供，并有对拍测试。

### 24. 自适应深度的所有调整都被静默吞掉

迭代加深只在**偶数层**步进，而所有调整都是 ±1。
实测：`max_depth` 从 8 提到 14 之后，10 局对拍**逐局完全相同** —— 加成从未生效。

**教训**：① 深度单位（树层 vs 玩家步）必须写进文档；
② 一类"永远不生效"的代码，靠**对拍结果完全相同**才能发现。

### 25. `max_depth` 正好等于 `base_depth`，所有加成被 clamp 掉

与上一条同源。放开到 14 之后必须**配合时间预算**使用，
否则危险局面的那一步会明显变慢。

### 26. 重要性采样：三次独立测量全部为负

试过 4+4、6+2、不同剪枝阈值组合。根因是 `total / weight_sum` 只对选中的分支归一化，
**系统性低估风险**。这条路已关闭。

**教训**：负结果也要写下来，否则以后还会有人再试一遍。

### 27. "每局耗时"不能当作可比的算力预算

**现象**：一次实验里"胜出"的配置每局 52 秒，基线 92 秒，看起来大赢。

**根因**：**赢了会让局数变长**，所以"每局时间"不是同一份算力。
在 101–300 号种子上重测：基线 96,529，那个配置只有 33,945–58,627。

**教训**：比较不同策略时要固定**算力**（固定深度或固定节点数），不能固定"每局时间"。

### 28. 测耗时前机器必须是干净的

踩过两次：一次是对着**改动前编译的二进制**跑实验（白跑），
一次是并行跑两个引擎任务导致每局耗时虚高。

**教训**：跑测量前核对**二进制时间戳 vs 源码时间戳**，并确认没有并行任务。

## 五、测量与验证：这一类的错误最伤

### 29. 一个不可靠的检查比没有检查更危险

**现象**：我加了一条"声明了却从不使用的 `el.xxx`"检查，它误报了
（`el.` 有直接调用与整对象传参两种用法，静态匹配区分不了）。
我依据误报**删掉了 6 个正在使用的声明**。

**教训**：检查本身的可靠性要先用已知样本验证。
**宁可不查，也不要查错** —— 现在那条降级成"提示（非失败）"。

### 30. 判据写错：`分数 >= 方块值之和`

**现象**：为验证"打断动画"是否弄丢方块，我用了这条判据，结果慢速跑（正常路径）
也被判成"丢了块"。

**根因**：判据本身是错的。两个 4 合成 8：分数 +8，而盘面 `8+8=16` 变成 `8`，**和反而变小**。

**教训**：**先用已知正确的路径验一遍判据**，通过再拿去测可疑路径。
改用"渲染层内部状态 vs DOM"对照后才靠谱。

### 31. 只看源码就宣布"改好了"

**现象**：好几轮"我改了 CSS，图标颜色应该变了" —— 用户三次回复"未变动"。

**根因**：**读源码觉得对 ≠ 浏览器算出来的值对**。

**教训**：UI 改动用真浏览器（Chromium）量**计算后的值**，
再用截图目视复核。项目的 `_tmp` 里有一套这样的核对脚本。

### 32. 测试环境里 `100dvh` 与 `innerHeight` 不一致（重复第 20 条，但值得单列）

因为它的后果是**基于错误数据继续优化**，比单纯的判断错误更费时间。

### 33. 用 `requestAnimationFrame` 做"让出"：后台标签页里整个循环停死

**现象**：用户在网页版切到别的标签页，自动演示**直接停住**，而且**切回来也不恢复**。
用户的原话是"之前我切换网页照样能跑，这次就不行了"。

**根因**：上一轮为修"手机上测试档一卡一卡"（主线程被循环占满、页面一帧都没重绘），
在自动演示的循环里加了"每步让出一帧"：

```js
await new Promise((resolve) => requestAnimationFrame(() => resolve()));
```

**`requestAnimationFrame` 在后台标签页里不触发**（浏览器不渲染那些页面），
于是这个 await 永远挂着 —— 循环不是变慢，是**已经死了**，所以切回来也不会恢复。

**教训**：

- 凡是把控制流挂在"回调一定会来"的 API 上，都要问一句**它什么时候不会来**；
- "让出执行权"这种基础设施**必须带兜底**（`setTimeout` 竞速），不能让单点依赖挂死整个循环；
- 页面不可见时本来就没有重绘需求，**根本不该去等帧** ——
  这只在真实浏览器里才暴露，**注意本机复现不出来**（见下）。

**⚠️ 这条我复现不出来，只能验证代码路径**：Playwright 无论 headless 还是有头，
切换标签页后 `visibilityState` 仍报 `visible`、`rAF` 照常触发（实测 119~122 次/秒）。
所以改为**构造两种环境验证代码路径**：

| 场景 | 预期 | 实测 |
|---|---|---|
| 前台正常 | 走 rAF | ✓ rAF |
| rAF 永不触发（桩） | 兜底定时器放行 | ✓ 54ms 内放行 |
| 页面不可见 | 走 setTimeout，不等帧 | ✓ 0ms |

这提醒一件事：**自动化环境测不到的，不等于没发生** —— 用户报告 + 已知的浏览器行为
+ 代码路径验证，三者合起来才够；不要因为"我复现不出来"就否定现象。

## 六、如果只记三条

1. **改动前先讲理解，等用户点头** —— 这一条能消掉本清单里最大的一类浪费（第 1、2、3 条）。
