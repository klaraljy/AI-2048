## 一句话

一个 2048 的 AI 实验室：C++ 引擎在固定种子集上跑批，用可复现的分数证明某个算法改动是不是真的更强；
附带一个动画和音效到位、能在 Windows 桌面和 Android 手机上手玩的前端。

## 给谁用

| 角色 | 他们做什么 | 他们得到什么 |
|---|---|---|
| **本人（AI 作者）** | 改算法 → 跑固定种子集 → 看平均分与最大块分布 → 决定留不留 | 一个能证伪自己直觉的实验台，而不是靠感觉 |
| **本人（玩家）** | 在电脑网页或**手机上**玩一局，或看 AI 自动玩 | 手感对、有动画音效的 2048；直观看到 AI 强到什么程度 |
| 旁观者（朋友/访客） | 打开页面或装个 App 看 AI 演示、自己试一局 | 不需要装任何开发环境就能看到结果 |

**主力角色是第一个。** 后两个是附属，不为它们做账号、排行、多人对战。

## 核心循环

```
1. 改一处算法或权重（C++）
2. 跑同一组固定种子，出平均分 / 最大块分布 / 每步耗时
3. 与上一版对照，判断这次改动是真进步还是噪声
4. 留下或回退，回到第 1 步
```

**循环多久跑一次？** 一次实验几分钟到十几分钟（取决于种子集规模）；
一天可以跑很多轮。人类玩一局是 1–10 分钟。

**第二条循环（附属，服务于"看见结果"）：**

```
打开网页或手机 App → 手动玩一局 或 点"AI 自动" → 看动画和音效 → 再来一局
```

## 平台上

| 平台 | 角色 | 内容 |
|---|---|---|
| Windows 桌面（浏览器） | **主力** | 完整实验室：跑批、统计、调参、对拍 + 可玩前端 |
| Android App | 附属 | **玩 + 看 AI 自动玩**。不带跑批/调参 |

**技术形态**：C++ 引擎做成**可移植静态库**，三处消费者共用同一份规则与算法 ——
桌面 WebSocket 服务、命令行跑批、Android（JNI）。这样"AI 跑的就是真实规则"这条
底线不会因为多一个平台而破掉（历史上参考原型的规则漂移就是这么发生的）。

iOS 暂不做：本机是 Windows，编译 iOS 需要 macOS + Xcode。

## 为什么值得做

| 问题 | 答案 |
|---|---|
| 凭什么有人用？现有方案哪里不够？ | 不缺 2048，缺的是**能证伪自己**的 2048 AI 工作台。网上多数 2048 AI 项目是"跑出来一个高分就发出来"，没有固定的种子集、没有改动前后的对照、也没有回归检测。而参考用的前端原型**不可复现**（`Math.random()` 未播种）、**调参结论不可信**（评估环境的规则和真实规则不一致）、**AI 分数与人玩的规则不是同一个游戏**（难度会把新块塞进四角，简单难度概率 70%）。这些坑正是这个项目要填的。 |
| 凭什么你做？你有什么别人没有的条件？ | 已经有一个**能跑、分层清晰、可作对照基线**的 JS 原型（1276 行纯计算 AI，零 DOM、零依赖），还有一个视觉基线不错的前端。所以第一天的起点不是"从零写 2048"，而是"把已知强度的基线搬到 C++，然后证明每一次改动"。这个起点比绝大多数从零开始的项目高一截。 |
| 凭什么现在做？ | 2048 的算法前沿已经很清楚：手工启发式的 expectimax 有天花板，而 **n-tuple 网络 + 时序差分学习**是公认更强的路线 —— 但这条路**在 JavaScript 里基本走不动**：训练要跑几十万到上百万局，JS 的 BigInt 位棋盘和单线程跑批撑不住。选 C++ 正好解锁这一档。 |

## 新颖点

**把"AI 到底有没有变强"变成一个可复现、可证伪的实验协议，而不是一次性的跑分。**

具体落法是三条绑定在一起的机制：

1. **固定种子集**：每个基准种子集有版本号，所有结果都带版本号，不同规则集/种子集下的分数禁止混排。
2. **对拍基线**：JS 原型保留为基线，C++ 版每次大改都要和它同种子对拍 —— 分数下降时先排除"是不是顺手把原型的 bug 改掉了"这个解释。
3. **回归检测**：分数掉了要显式发现并记录，而不是当作噪声忽略。

## 范围

### 做

- C++ 引擎：标准 2048 规则、种子化 PRNG、确定性可复现、跑批与统计
- 引擎形态：**可移植静态库**，桌面服务 / 命令行 / Android 三处共用
- 前端（桌面）：方块**滑动 / 合并 / 新块出现**动画、音效、键盘 + 触屏滑动、撤销、最高分持久化、游戏结束与 2048 庆祝
- Android App：可玩 + AI 自动演示；AI 强度可调（按时间预算降级）
- AI 算法：先 expectimax 基线，再上 n-tuple + TD（见下文「AI 算法路线」）
- 基准资产：固定种子集 + 历史结果留档

### 不做（非目标）

> 用核心循环反推：不服务于"改算法 → 跑批 → 看分"这个循环的，默认进这里。

- ❌ 不做账号系统、登录、云同步
- ❌ 不做在线排行榜、不做多人对战、不做联机
- ❌ 不做 iOS（需要 macOS + Xcode，本机不具备）
- ❌ 不做 3D / 花哨主题商城 / 皮肤系统
- ❌ **不保留原有的"难度改方块生成规则"做法**（会把 AI 分数变得不可比）
- ❌ 不做 LLM 决策路线（把棋盘喂给大模型选方向）—— 那是另一个产品
- ❌ 不做商业化、不做广告、不做用户增长
- ❌ 不做通用博弈框架 / 插件系统（只服务 2048）
- ❌ 不做 macroxue 的超大预计算查找表路线（27GB 内存 / 18GB 磁盘，本机不可能）

### 以后可能做

- 前端天梯看板：提交一次跑批结果，自动出图对比多个版本
- 在浏览器里实时看 AI 的搜索树 / 各方向评分（教学向）
- 让 AI 之间对战比较（不同权重各跑同一种子集，出对拍图）
- 5×5 或 6×6 等变体棋盘
- iOS 版本（等有 Mac 之后）

| 5 | 跑批 + 结果留档 | 一条命令跑完种子集，输出平均分、最大块分布、per-move 耗时，存进 `docs/results/` | 未开始 |

> 里程碑 6 排在算法升级之前：因为"能装进手机日常用"是这个项目明确的目标，
> 而它会影响引擎的接口设计（时间预算、无网络依赖、无文件系统依赖）。

## AI 算法路线

> 已调研（2024–2025 视角）。以下数字都有一手来源，可查证。

### 各条路线的实测强度

| 路线 | 平均分 | 32768 到达率 | 65536 到达率 | 来源 |
|---|---|---|---|---|
| 手写启发式 expectimax，depth 3 | 493,000 | — | 1.3% | macroxue/2048-ai |
| 手写启发式 expectimax，depth 5 | 661,000 | — | — | macroxue/2048-ai |
| **手写启发式 expectimax，depth 8** | **711,769**（1000 局） | **80.5%** | **3.5%** | macroxue/2048-ai |
| nneonneo expectimax，depth 8（100 局） | median 387,222 | 36% | 0% | nneonneo/2048-ai |
| n-tuple + TD-afterstate，1-ply（Szubert 2014） | ~100,000 | 0% | 0% | arXiv:1606.07374 |
| n-tuple + TC + 多阶段，1-ply | 250,000–320,000 | 19% | 0% | Jaśkowski 2018 |
| n-tuple + expectimax 3-ply / 时间预算 | 491,398–609,104 | 50–70% | 0% | Jaśkowski 2018 |
| **n-tuple + TD/TC + tile-downgrading，6-ply** | **625,377** | **72%** | 0.02% | TDL2048+ / arXiv:2111.11090 |
| MCTS / deep RL | 无公开的 32768+ 成绩 | — | — | 判断为明显不如上两条 |

**关键结论：当前 SOTA 不是"二选一"，而是两者的组合 —— 用 n-tuple 网络学出来的评估函数
塞进 expectimax 做 3–6 ply 搜索。** 纯 n-tuple 1-ply 打不过纯 expectimax 深搜；
`625k / 72%` 那条正是"学出来的评估 + 期望层搜索"。

### 各条路的代价

| 路线 | 工程量 | 内存 | 训练时间 | 风险 |
|---|---|---|---|---|
| expectimax + 手写启发式 | 中（几周） | 小 | 无训练 | 低。算法直白，错了能看出来 |
| expectimax + 超大预计算表（macroxue 路线） | 中大 | **27GB 内存 / 18GB 磁盘** | 无训练，但要生成表 | 中。本机不可能 |
| n-tuple + TD 学习 | **大**（一个训练框架） | 67M 参数 ≈ 134MB 起步，SOTA 量级 1.07e9 参数 ≈ 2GB+ | 1e10 actions | **高**。TD 实现极易悄悄写错且看不出来 |

### 已定路线：先 expectimax，再 n-tuple

理由：

1. **先拿到一个能用的东西。** bitboard + 行查找表 + depth 6 expectimax + TT + 根并行。
2. **两条路共享底座。** n-tuple 路线一样需要 64-bit 位棋盘、行查找表、快速走子、
   种子化跑批。先做 expectimax 不会白做。
3. **n-tuple 的风险主要是"悄悄错了"。** TD 更新里最容易出错的几处
   （终局 `δ = -V(s')`、afterstate 与 state 索引混淆、α 是否按 tuple 数归一化、
   `λ^(t-k)` 衰减方向、多阶段切换时点）**都不会报错，只会让分数低一点** ——
   而没有基线就无法判断"低一点"是 bug 还是正常。
   所以正确顺序是：**先用 expectimax 立一个可信基线，再往上叠 n-tuple，逐阶段对拍。**
4. n-tuple 的训练验收有明确标尺：**先在小网络（17 个 4-tuple）上复现
   Szubert 的 ~100k / 97% 胜率**，复现成功才放大到 67M 参数。

### 阶段与预期（用于排里程碑）

| 阶段 | 预期平均分 | 32768 率 | 主要工作 |
|---|---|---|---|
| C++ 位棋盘 + 行查找表 + TT + depth 6 | 400k–600k | 30–70% | 位棋盘/查表正确性、TT、概率剪枝 |
| + 根并行 | 600k+ | — | 多线程确定性 |
| + n-tuple 学出的评估 + expectimax 3–6 ply | 500k–610k | 50–70% | 期望层与 n-tuple 的结合、模型加载 |
| + optimistic TD/TC + tile-downgrading | 625k | 72% | OI 调参、多阶段网络 |

> 注意最后两行：**更强的评估函数不一定立刻带来更高分数**，要靠搜索层数补回来。
> 这正是本项目「用分数说话 + 保留对拍基线」这套机制存在的意义。

### 已知的坑

- **expectimax 不能用 alpha-beta**：没有 min 节点。只能按累计概率阈值砍分支。
- **不用游戏真实分数当启发式**：会过度鼓励立刻合并。用 空格 / 单调性 / 平滑度 / 合并潜力。
- **单调性要按 tile 等级加权**：让大数字的不单调被重罚，这是强启发式的关键细节。
- **BMI2 的 `PEXT` 在 AMD Zen1/Zen2 上极慢**，n-tuple 索引要考虑非 BMI2 回退路径。
- **内存是真瓶颈**：n-tuple SOTA 量级 1.07e9 参数，权重用 2 字节浮点也要 2GB+；
  训练必须定期 checkpoint（TDL2048 专门有模型损坏检查脚本，说明这问题真实发生过）。
- **131072 是否真被达成，未找到一手证据** —— 理论最大瓦片是 131072，
  但只有商业站点声称达成过。**不得把这条写成事实。**
- **理论极限**：严格证明存在打 2048 胜率 ≥ 0.99969 的策略，
  但"概率 1 保证达成"的瓦片只有 **256**（arXiv:2303.07266）。

## 前端缺口清单

> 参考原型**完全没有音频**（全库 grep `Audio/sound/.mp3/.wav` = 0 命中），
> 也**完全没有动画**（`.tile` 上那条 `transition` 是死代码：JS 从不设 transform，节点每步被重建）。

| 缺口 | 现状 | 目标 |
|---|---|---|
| 方块滑动动画 | 无。每步 `innerHTML=""` 重建 16 个节点，方块没有身份 | 方块持有持久 id + 绝对定位 + transform 过渡 |
| 移动轨迹数据 | 无。`move()` 只返回 `{board, moved, gained}` | 引擎输出每块的 from/to/是否合并 |
| 合并弹跳 | 无 | merge pop |
| 新块出现 | 无 | scale-in + fade |
| 音效 | **完全没有** | 滑动 / 合并 / 新块 / 胜利 / 失败 + 静音开关 |
| 触屏操作 | **完全没有**（无 touch/pointer 监听、无方向按钮）→ 手机上无法玩 | 滑动手势 + 可选方向键 |
| 撤销 | **没有实现**（按钮只弹提示"暂未接入"） | 真正的状态栈 |
| 最高分持久化 | 无（`localStorage` 全库 0 命中），刷新即丢 | localStorage |
| 游戏结束 | 只改一行状态文字 | 遮罩层 + 再来一局 |
| 得分浮字 | 无 | `+4` 浮字 |
| 输入锁 | 无（长按会连发） | 动画期间锁输入 / 入队 |
| `prefers-reduced-motion` | 无 | 加动画时必须补 |

**配色**：2…2048 沿用经典 Gabriele Cirulli 调色板（`#eee4da` → `#edc22e`），
2048 以上原型的自选配色覆盖到 2^20，超过则全部同色。
目标：配色成体系（含暗色模式可选），并保证 AI 能走到的每个值都可区分。
